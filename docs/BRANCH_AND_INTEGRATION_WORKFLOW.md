# 開發分支、整合審查與合併規則

自 2026-10-25 起，新增功能或修復程式時，原則上不得直接提交到 main。

## 標準流程
1. **確認基線**：先讀取目前 main 的專案索引、相關場景／腳本、依賴模組、存檔格式與近期提交；並搜尋之前已新增的功能，確認是否已有相同或重疊實作。
2. **建立功能分支**：從最新 main 建立短期分支。
3. **小步修改**：每個分支聚焦一個可審查的變更，不以多個獨立 patch 代替整合後的完整專案。
4. **整合影響分析**：列出修改檔案的所有呼叫端、資料來源、存檔格式、場景節點、輸入映射、訊號與下游功能；將先前已加入的功能納入檢查。
5. **靜態檢查**：檢查 GDScript 語法／型別、場景路徑、節點生命週期、訊號、輸入映射、存檔相容性、重複資料來源及呼叫端。
6. **執行測試**：有 Godot 4 時，至少做專案解析／啟動、受影響功能測試及回歸測試；記錄引擎版本、測試步驟、結果與錯誤。若沒有引擎，必須標示未執行，不能聲稱通過。
7. **建立 Pull Request**：將功能分支提議合併到 main，列出變更、測試證據、已知限制、風險及回滾方式。
8. **審查差異**：檢查 PR 的 Files changed，確認沒有意外刪檔、重複模組或不相關變更；確認新功能與舊系統整合，而非只獨立存在。
9. **通過後才合併**：只有審查與必要測試完成後才合併。未測試或有未解阻斷問題的版本保持未合併。
10. **同步紀錄**：合併後更新 PROJECT_INDEX.md 與 Notion，記錄 commit、版本、檔案、測試狀態及未解問題。

## 必做整合檢查
- **單一資料來源**：避免背包、負重、存檔各自維護重複狀態。
- **相容性**：檢查舊存檔、舊場景、現有輸入與資源路徑。
- **生命週期**：節點建立、移除、重複載入時，不得留下重複節點、訊號或標籤。
- **回歸測試**：修改某系統後，重跑所有受影響的舊功能。
- **可追溯性**：每個程式變更都要有 GitHub commit；Notion 記錄必須與實際狀態一致。

## 狀態用語
- **已提交**：GitHub 有 commit。
- **已開 PR**：變更等待審查，尚未進入 main。
- **已合併**：變更已進入目標分支。
- **已解析／已啟動／已遊玩測試**：分開記錄，不可互相替代。
