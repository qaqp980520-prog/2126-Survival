# 共用背包 × M1.3 存檔 Schema 相容性審查｜2026-10-25

## 版本與狀態
- 版本：M0.4 靜態審查記錄
- 分支：`audit/inventory-save-schema-compat-2026-10-25`
- 基底：`main`
- 類型：靜態程式碼審查與測試規格；沒有修改執行時背包程式。
- Godot 4 驗證：尚未執行。這份文件不是測試通過證明。

## 已確認的系統邊界
1. `systems/SurvivalInventory.gd` 使用 `schema_version: 1`，資料放在 `inventory`，遊戲日放在 `game_day`。
2. M1.3 存檔修補以頂層 `version: 1|2` 保存資料，背包位於 `inventory`，遊戲日也是 `game_day`，另有快捷欄、玩家座標和 `world_state`。
3. `systems/SurvivalWorldBridge.gd` 的 `serialize_inventory()` / `restore_inventory()` 只處理共用背包字典，不等於完整的 M1.3 世界存檔。
4. PR #4 的注入接口可以讓橋接器引用同一個背包物件，但還沒有把 M1.3 的舊 `inventory` Dictionary 接到這個物件。不能直接把兩種存檔字典互相傳入。

## 靜態發現（尚未修正）
- **格式版本不同**：共用背包是 `schema_version`，世界存檔是 `version`。需要明確的轉換函式，不能依賴默認值或直接互傳。
- **小數數量會被截斷**：`load_save_dict()` 接受 float 數量，負數檢查使用 `int(value)`；例如 1.9 可能通過並在後續重量／數量計算被轉為 1。建議只接受有限且非負的整數數量。
- **遊戲日型別／範圍不足**：目前 `game_day` 以 `int()` 轉換並夾到至少 1；損壞的小數、字串或過大數值可能被悄悄轉換／接受。應在修改任何狀態前驗證。
- **未知物品 ID 重量為零**：`ITEM_WEIGHTS.get(item_id, 0.0)` 使未登記物品可進入背包且不增加重量。這可能是未來擴充需求，也可能是漏洞；應先決定採用明確物品登錄表，或允許擴充 ID 並要求重量定義。
- **載入不是完整原子驗證**：目前在驗證所有欄位前，缺乏版本與遊戲日的嚴格檢查。修正時應先驗證到暫存字典，全部通過後才替換 `counts` / `game_day`，確保失敗時舊背包不變。
- **橋接器生命週期**：`bind_inventory()` 必須在拾取／採礦之前呼叫；需在 Godot 中驗證 `_ready()` 不會覆蓋注入實例，並確認 UI／角色控制器讀取的是同一個實例。

## 回歸測試規格
### A. 共用背包資料
- 有效整數數量與遊戲日可往返序列化。
- 缺少已知物品欄位時，預設補 0。
- 負數、字串、NaN／Infinity（若可由輸入路徑產生）、小數數量、錯誤 schema 版本必須拒絕。
- 任何拒絕載入的情況，原本的 `counts` 與 `game_day` 保持不變。
- 未知物品 ID 的處理符合已選定的物品登錄策略。
- 過大數值不得造成負重溢出或不合理負重。

### B. 世界存檔相容性
- 頂層 v1 與 v2 世界存檔仍由 M1.3 驗證器處理。
- 世界存檔內的背包數量轉換為共用背包格式後再載入；轉換需保留遊戲日與所有有效物品數量。
- 壞掉的背包資料不得部分套用玩家座標、快捷欄、體力或作物狀態。
- 重複讀檔兩次不增加作物節點／互動清單數量。

### C. 世界橋接與負重
- 拾取和採礦都更新同一個背包實例。
- 丟棄物品後重量與負重狀態立即重算。
- 超過負重上限時移動倍率正確；超過 90 kg 時不可跳躍。
- 存檔／讀檔往返後，數量、遊戲日、重量、負重狀態一致。
- 沒有注入背包時，橋接器仍保留原本建立預設背包的行為。

## 建議實作順序
1. 在獨立分支先為 `SurvivalInventory.load_save_dict()` 加上嚴格、原子式驗證及測試。
2. 設計一個明確的 M1.3 世界存檔 ↔ 共用背包轉換函式，不改動世界存檔頂層格式。
3. 在乾淨副本套用並檢查 M1.3.1–M1.3.4 修補，確認沒有重複／衝突。
4. 在 Godot 4 執行 parser、腳本測試、場景啟動及存檔往返。
5. 只有上述測試通過後，才將橋接器掛入 M1.3 世界場景；不提前合併到 `main`。
